# Архитектурные решения и допущения

- **Пакетная обработка и дедупликация.** Объединены в отдельном классе `DeduplicatedBatcher`, который отвечает за группировку операций и устранение дубликатов в пределах одного окна пакетной обработки.

- **Предотвращение дубликатов.** Отдельные ключи идемпотентности не используются. Повторное добавление одного элемента и повторный выбор уже выбранного элемента корректно обрабатываются за счёт технических гарантий на уровне базы данных и логики операций.

- **Хранение данных.** Используется SQLite в режиме in-memory. Реляционная модель и индексы позволяют использовать стандартные возможности базы данных для фильтрации и пагинации без необходимости самостоятельно реализовывать структуры данных и оптимизировать базовые сценарии поиска.

- **Порядок выбранных элементов.** Для хранения порядка используются лексикографические позиции. Это позволяет вставлять элементы между существующими позициями без массового обновления остальных элементов и периодической ребалансировки порядка.

- **Бесконечная прокрутка.** Используется двунаправленная пагинация с окном из пяти страниц. Это ограничивает объём одновременно хранимых на клиенте данных. После мутаций на сервере обновляется только ограниченная часть уже загруженного списка, а не весь объём данных.

- **Обновление после мутаций.** Инвалидация и обновление данных выполняются с небольшой задержкой после завершения мутаций, чтобы объединить несколько изменений в один рефреш и не выполнять отдельный рефреш после каждой мутации.

- **REST API.** Выбран классический REST API. WebSocket также рассматривался, в том числе для того, чтобы не поддерживать множество HTTP-соединений для операций, объединённых в один батч, но в итоге выбран более простой request/response-подход.

# Запуск

Разработка (в отдельных терминалах): `npm run dev:backend` и `npm run dev:frontend`.

Прод: `docker compose up`.
